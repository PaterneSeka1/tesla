## 3. Vision produit

Je souhaite que Nikola Tesla Académie devienne une véritable aventure pédagogique interactive.

Je veux qu'un routier puisse ouvrir Tesla par plaisir, explorer des contenus, découvrir de nouvelles connaissances, jouer, relever des défis et progresser naturellement.

Je souhaite créer une expérience suffisamment intéressante pour qu'un routier puisse volontairement y consacrer une ou deux heures, sans avoir constamment l'impression d'étudier ou de passer des examens.

Il doit avoir envie de découvrir la suite.

Il doit pouvoir apprendre sans pression inutile.

Il doit pouvoir revenir facilement après une interruption.

Il doit ressentir un véritable sentiment d'accomplissement.

Tesla doit être une application :

- Moderne.
- Immersive.
- Ludique.
- Interactive.
- Vivante.
- Fluide.
- Intuitive.
- Accessible.
- Originale.
- Performante.
- Évolutive.
- Respectueuse des valeurs scoutes.

L'objectif n'est pas de créer une application addictive.

L'objectif est de rendre l'apprentissage intrinsèquement intéressant.

# PARTIE II — SIMPLICITÉ ABSOLUE DE L'EXPÉRIENCE

## 6. Règle fondamentale : aucune information inutile

Cette exigence est prioritaire et s'applique à toute l'application.

Je ne veux aucune information inutile qui surcharge les interfaces.

Chaque élément affiché doit répondre à au moins une des questions suivantes :

1. Permet-il à l'utilisateur de réaliser une action ?
2. Permet-il de comprendre une information nécessaire ?
3. Permet-il de prendre une décision ?
4. Permet-il de s'orienter ?
5. Apporte-t-il une valeur pédagogique réelle ?
6. Améliore-t-il réellement l'immersion ?

Si la réponse est non à toutes ces questions, supprimer l'élément de l'interface.

Cette règle concerne :

- Les titres.
- Les sous-titres.
- Les descriptions.
- Les paragraphes introductifs.
- Les badges.
- Les cartes.
- Les statistiques.
- Les boutons.
- Les alertes.
- Les icônes.
- Les illustrations.
- Les filtres.
- Les menus.
- Les tableaux.
- Les widgets.
- Les animations.

Ne pas confondre richesse fonctionnelle et quantité d'informations affichées.

Une fonctionnalité peut exister sans être constamment visible.

## 7. Audit de la surcharge visuelle

Auditer toutes les pages de Tesla.

Identifier systématiquement :

- Les informations répétées.
- Les titres affichés plusieurs fois.
- Les descriptions évidentes.
- Les textes expliquant ce que le bouton indique déjà.
- Les cartes contenant trop peu d'informations utiles.
- Les statistiques sans action associée.
- Les badges décoratifs.
- Les libellés techniques.
- Les boutons redondants.
- Les informations administratives visibles par les routiers.
- Les filtres rarement utilisés.
- Les espaces excessivement vides.
- Les informations secondaires occupant une place principale.
- Les encadrés imbriqués inutilement.
- Les éléments qui compliquent le parcours.

Pour chaque élément identifié, décider de manière argumentée :

- Le conserver.
- Le simplifier.
- Le déplacer.
- Le regrouper.
- Le masquer derrière une action.
- Le supprimer de l'interface.

La suppression d'une information visuelle ne signifie pas la suppression de la donnée correspondante dans la base.

## 8. Exemples de simplification attendue

Ne pas afficher :

« Bienvenue sur votre espace pédagogique personnalisé. Retrouvez ci-dessous l'ensemble des informations concernant votre parcours de formation et votre progression. »

Afficher simplement :

« Prêt pour la suite de l'aventure ? »

Ne pas afficher simultanément :

- Nombre total de modules.
- Nombre de modules accessibles.
- Nombre de modules disponibles.
- Nombre de modules terminés.
- Nombre de modules restants.
- Pourcentage de progression.
- Nombre de leçons.
- Nombre de questionnaires.
- Nombre de tentatives.

Afficher uniquement les informations utiles dans le contexte immédiat.

Par exemple :

« Histoire du scoutisme — 3 haltes sur 5 »

Bouton : « Continuer ».

Les statistiques détaillées peuvent être disponibles dans le carnet personnel.

Ne pas afficher un badge « Disponible » sur tous les contenus lorsque leur disponibilité est déjà évidente.

Ne pas afficher un statut technique si celui-ci ne change aucune décision de l'utilisateur.

Ne pas répéter le nom Nikola Tesla Académie dans toutes les sections.

Ne pas afficher les identifiants techniques, les noms de permissions, les rôles internes ou les informations de fonctionnement du backend.

## 9. Divulgation progressive

Mettre en place le principe de progressive disclosure.

L'utilisateur découvre les fonctionnalités au moment où il en a besoin.

Exemples :

- Les détails d'un badge apparaissent lorsqu'il le sélectionne.
- L'historique des résultats se trouve dans le carnet personnel.
- Les préférences sont accessibles depuis le profil.
- Les filtres avancés apparaissent uniquement à la demande.
- Les informations complémentaires d'une leçon sont accessibles sans encombrer sa lecture.
- Les règles d'un jeu apparaissent lorsqu'il est découvert pour la première fois ou sur demande.
- Les informations hors ligne détaillées sont accessibles depuis la gestion de l'appareil.

Ne pas tout afficher sur l'accueil.

Ne pas multiplier les pages pour cacher la complexité.

Ne pas ajouter plusieurs menus pour accéder à une fonctionnalité simple.

## 10. Une action principale par écran

Chaque écran doit posséder une intention principale claire.

Exemples :

- Accueil : continuer mon aventure.
- Lecture : continuer la découverte.
- Bibliothèque : sélectionner un contenu.
- Défi : jouer.
- Fin de mission : continuer, revoir ou terminer.
- Profil : consulter ou gérer ses informations.
- Éditeur : enregistrer ou publier selon les droits.

Les actions secondaires doivent avoir une importance visuelle inférieure.

Ne pas afficher plusieurs boutons primaires concurrents.

L'utilisateur doit comprendre immédiatement ce qu'il peut faire.

## 21. Hiérarchie des animations

Définir quatre catégories.

### Micro-interactions

Interactions rapides sur les boutons, cartes, réponses et contrôles.

Durée indicative : 100 à 180 ms.

### Transitions

Changements de contenu, d'écran ou d'état.

Durée indicative : 180 à 300 ms.

### Accomplissements

Réussite d'une mission, obtention d'un badge, progression importante.

Durée indicative : 400 à 800 ms.

### Animations exceptionnelles

Moments particuliers et significatifs.

Elles doivent rester rares et pouvoir être ignorées.

Ne pas afficher des confettis à chaque réponse correcte.

Ne pas faire attendre l'utilisateur pour continuer.

Respecter `prefers-reduced-motion`.

Prévoir une préférence de réduction des animations.

Les sons doivent être désactivés par défaut ou activés explicitement.

Prévoir un contrôle centralisé des préférences.

Aucune lecture sonore automatique intrusive.

# PARTIE V — NAVIGATION ET ACCUEIL

## 23. Navigation simplifiée

La navigation doit être pensée mobile-first.

Pour le routier, privilégier une barre inférieure contenant au maximum cinq destinations principales.

Proposition :

- Accueil.
- Explorer.
- Défis.
- Mon parcours.
- Profil.

Analyser la pertinence réelle de chaque destination.

Réutiliser les routes existantes.

Ne pas introduire des pages qui dupliquent des pages actuelles.

Les anciennes routes doivent rester fonctionnelles ou disposer de redirections compatibles.

Les accès doivent rester gouvernés par les permissions existantes.

Ne jamais afficher les rôles techniques.

## 24. Barre inférieure mobile

Prévoir :

- Des icônes reconnaissables.
- Des libellés courts.
- Un état actif visible.
- Des zones tactiles adaptées.
- Le respect des safe areas.
- Une position stable.
- Une transition subtile.
- Un comportement adapté au clavier.

La barre inférieure ne doit pas :

- Masquer le contenu.
- Occuper inutilement une grande hauteur.
- Contenir des sous-menus complexes.
- Rester affichée pendant une expérience immersive lorsque cela gêne.

Pendant un jeu ou une leçon immersive, utiliser une interface de concentration avec un bouton de retour clairement identifiable.

## 25. Accueil routier

Repenser l'accueil comme un véritable point de départ.

Ne pas afficher un tableau de bord administratif.

Structure recommandée :

1. Un en-tête compact.
2. Une aventure principale à reprendre.
3. Une action principale.
4. Une suggestion pertinente de défi ou de révision.
5. Éventuellement une information importante de la communauté.

Ne pas transformer cette structure en obligation d'afficher cinq cartes.

Adapter le contenu à l'état réel du routier.

Exemple :

« Prêt à reprendre la Route ? »

Histoire du scoutisme

Halte 3 sur 5

Bouton : « Continuer mon aventure »

Plus bas, si pertinent :

« Un défi de 5 minutes ? »

Ne pas afficher toutes les statistiques, tous les badges, toutes les activités et tous les modules sur l'accueil.

## 26. Accueil intelligent

L'accueil doit s'adapter à différents états :

- Première connexion.
- Aventure commencée.
- Aucune leçon commencée.
- Nouveau contenu publié.
- Entraînement disponible.
- Révision pertinente.
- Rattrapage nécessaire.
- Défi terminé.
- Retour après une absence.
- Aucun contenu disponible.
- Connexion hors ligne.
- Parcours terminé.

Utiliser des règles déterministes et explicables.

Ne pas utiliser une API d'IA pour générer inutilement ces recommandations.

Ne pas afficher de suggestion artificielle uniquement pour remplir l'écran.

## 27. Onboarding discret

Lors de la première utilisation, présenter les fonctionnalités essentielles progressivement.

Ne pas imposer un long tutoriel.

Prévoir :

- Une première action simple.
- Une courte découverte interactive.
- Des indications contextuelles.
- La possibilité d'ignorer.
- La possibilité de revoir les explications.

Ne pas afficher de tutoriel à chaque connexion.

Ne pas empêcher un routier expérimenté d'accéder immédiatement aux contenus.

# PARTIE VI — AVENTURE ET CONTENUS PÉDAGOGIQUES

## 28. Carte d'aventure

Faire évoluer la présentation du parcours pédagogique vers un sentier interactif.

Correspondances possibles :

- Module : destination.
- Leçon : halte.
- Exercice : défi.
- Ensemble de leçons : expédition.
- Révision : retour sur les traces.
- Évaluation officielle : défi officiel.
- Rattrapage : itinéraire de préparation.

Ces appellations constituent des propositions et ne doivent pas remplacer aveuglément les termes pédagogiques nécessaires.

Utiliser les données existantes comme source de vérité.

Créer une carte pouvant présenter :

- Des destinations.
- Des sentiers.
- Des étapes.
- Des haltes.
- Des points de découverte.
- Des défis.
- Des accomplissements.

La carte doit rester lisible sur un petit écran.

Éviter une carte gigantesque obligeant à effectuer de nombreux défilements pour atteindre un contenu.

Prévoir une vue classique alternative.

## 29. États de progression

Distinguer clairement :

- Découverte d'un contenu.
- Lecture commencée.
- Lecture terminée.
- Entraînement réalisé.
- Évaluation officielle disponible.
- Évaluation officielle en attente.
- Résultat accepté.
- Acquis validé.
- Progression ludique.

Ne pas fusionner ces états.

Ne pas afficher tous les états simultanément.

Présenter uniquement le statut pertinent dans le contexte.

Les cours publiés doivent rester librement consultables conformément aux règles existantes.

Ne jamais verrouiller artificiellement un cours avec des XP, des badges ou des niveaux ludiques.

## 30. Conservation intégrale des contenus

Le contenu pédagogique actuel est une force du projet.

Ne pas supprimer :

- Les cours.
- Les modules.
- Les leçons.
- Les textes officiels.
- Les prières.
- Les références.
- Les citations.
- Les sources.
- Les contenus publiés.
- Les versions.
- Les questionnaires.
- Les historiques.

Ne pas remplacer des contenus pédagogiques fiables par des résumés superficiels.

Ne pas générer de nouvelles informations historiques sans source ou validation.

L'objectif est d'améliorer la manière d'apprendre.

## 31. Lecteur pédagogique classique et immersif

Conserver un mode de lecture classique.

Ajouter ou enrichir un mode immersif.

Le mode immersif doit pouvoir présenter le contenu sous forme de séquences courtes et intéressantes.

Types d'interactions possibles :

- Découverte progressive.
- Cartes à retourner.
- Frises chronologiques.
- Images interactives.
- Anecdotes.
- Révélations.
- Questions de compréhension.
- Illustrations annotées.
- Associations.
- Exercices de mémorisation.
- Mises en situation.
- Synthèses.

L'utilisateur doit pouvoir passer au contenu intégral sans perdre sa position.

Ne pas obliger l'utilisateur à cliquer vingt fois pour lire un paragraphe.

Ne pas découper les contenus de manière artificielle.

Ne pas cacher des informations pédagogiques nécessaires.

## 32. Exemple d'expérience : histoire du scoutisme

Transformer un contenu existant en une expérience comprenant :

- Une introduction narrative.
- Une représentation de l'époque.
- La découverte des personnages.
- Une frise chronologique.
- Des anecdotes vérifiées.
- Des questions intégrées.
- Une activité d'association.
- Une synthèse finale.
- Un entraînement facultatif.

L'utilisateur peut choisir de lire le contenu complet ou de suivre l'expérience interactive.

Les informations historiques doivent rester conformes aux sources existantes.

Ne pas fabriquer des dialogues historiques ou des événements fictifs présentés comme réels.

## 33. Exemple d'expérience : Loi scoute

Proposer :

- La consultation du texte complet.
- La découverte progressive des articles.
- Des scénarios de la vie quotidienne.
- Des associations entre situations et valeurs.
- Des questions de réflexion.
- Des exercices de mémorisation.
- Des activités de mise en pratique.

Les scénarios ne doivent pas réduire les valeurs scoutes à une logique simpliste de bonnes et mauvaises personnes.

Les exercices nécessitant un discernement humain doivent conserver cette dimension.

## 34. Exemple d'expérience : prières et textes de référence

Permettre :

- La lecture intégrale.
- La mémorisation progressive.
- Le texte à compléter.
- La remise en ordre.
- La répétition.
- Une lecture audio facultative si un contenu autorisé est disponible.

Ne pas altérer les textes officiels.

Ne pas transformer les prières en compétition.

Ne pas attribuer une valeur spirituelle à un score ou à un niveau ludique.

Respecter le caractère des contenus religieux et des engagements scouts.

## 35. Continuité entre les expériences

Le parcours doit être fluide.

Exemple :

Découvrir une leçon → comprendre une notion → relever un petit défi → obtenir un feedback → poursuivre ou quitter librement.

Ne pas obliger l'utilisateur à revenir systématiquement sur l'accueil entre deux activités.

Ne pas multiplier les écrans intermédiaires.

Conserver une progression claire.

Prévoir des points d'arrêt naturels.

Sauvegarder la position automatiquement.

# PARTIE VII — ÉDITEUR PÉDAGOGIQUE

## 36. Enrichir l'éditeur existant

Auditer l'éditeur Tiptap et les modèles de contenu existants.

Conserver la possibilité de :

- Créer des modules.
- Modifier les brouillons.
- Ajouter des leçons.
- Ajouter des leçons à des modules existants.
- Réorganiser les leçons.
- Prévisualiser.
- Soumettre.
- Approuver.
- Publier.
- Consulter les versions.

Étendre progressivement les fonctionnalités.

Ne pas remplacer l'éditeur existant sans justification.

## 37. Blocs pédagogiques interactifs

Créer un registre extensible de blocs.

Exemples :

- Texte.
- Image.
- Citation.
- Anecdote.
- Frise chronologique.
- Carte de mémorisation.
- Association.
- Question intégrée.
- Mise en situation.
- Révélation progressive.
- Point essentiel.
- Illustration annotée.
- Résumé.
- Défi interactif.

Chaque bloc doit disposer :

- D'un schéma de validation.
- D'une représentation dans l'éditeur.
- D'un rendu côté apprenant.
- D'un comportement hors ligne.
- D'une solution de repli accessible.
- D'une représentation imprimable lorsque pertinent.
- D'une compatibilité avec le versionnement.

Ne pas créer de blocs purement décoratifs sans usage pédagogique.

## 38. Simplicité de création pour les chefs

L'encadrement ne doit pas avoir besoin de savoir programmer.

Prévoir :

- Une bibliothèque de blocs.
- Des modèles réutilisables.
- Des champs simples.
- Un aperçu immédiat.
- Une réorganisation accessible.
- Un enregistrement automatique fiable.
- Des états de sauvegarde clairs.
- Des messages d'erreur utiles.

Proposer des paramètres avancés uniquement à la demande.

Ne pas afficher vingt paramètres techniques pour ajouter une question.

## 39. Compatibilité avec les anciens contenus

Tous les documents existants doivent rester lisibles.

Les nouvelles fonctionnalités ne doivent pas nécessiter une migration manuelle de tous les modules.

Prévoir :

- Des valeurs par défaut.
- Des adaptateurs si nécessaires.
- Des schémas rétrocompatibles.
- Des migrations additives.
- Des tests sur des contenus anciens.
- Un mode classique de repli.

Ne pas modifier automatiquement les versions publiées.

Les améliorations éditoriales doivent respecter le workflow d'approbation existant.

# PARTIE VIII — MOTEUR DE JEUX PÉDAGOGIQUES

## 40. Architecture du moteur de jeux

Créer ou enrichir un moteur extensible permettant d'ajouter de nouveaux jeux sans modifier toute l'application.

Auditer d'abord le moteur de quiz existant.

Séparer :

- Le contenu pédagogique.
- Les types de questions.
- Les règles de jeu.
- Le rendu graphique.
- Les animations.
- Les réponses.
- La notation.
- Les récompenses.
- La sauvegarde.
- La synchronisation.

Plusieurs jeux doivent pouvoir utiliser la même banque d'entraînement autorisée.

Ne pas dupliquer inutilement les questions.

Utiliser un registre de modes de jeu plutôt qu'une accumulation de conditions dans un composant gigantesque.

## 41. Salle de jeux pédagogiques

Créer une destination permettant de découvrir les jeux disponibles.

Ne pas reproduire un catalogue excessivement chargé.

Organiser les jeux selon leur utilité réelle.

Exemples :

- Réviser rapidement.
- Tester sa mémoire.
- Explorer un sujet.
- Relever un défi.
- Jouer avec son équipe.

Le routier doit pouvoir lancer rapidement un jeu.

Ne pas imposer une configuration complexe avant de commencer.

Prévoir un accès direct aux jeux pertinents depuis les cours.

## 42. Jeu du millionnaire scout

Auditer et enrichir le mode existant s'il est déjà implémenté.

Créer une expérience originale inspirée du principe du jeu du millionnaire.

Prévoir :

- Une question à la fois.
- Des paliers de progression.
- Une difficulté configurable.
- Des transitions immersives.
- Des jokers en entraînement.
- Un feedback pédagogique.
- Une reprise après interruption.
- Une fin de partie claire.

Jokers possibles :

- Éliminer certaines mauvaises réponses.
- Obtenir un indice.
- Passer une question.
- Consulter une notion de référence lorsque autorisé.

Les jokers doivent être réservés à l'entraînement, sauf règle officielle explicitement approuvée.

Ne pas copier les logos, musiques, habillages ou éléments protégés d'émissions existantes.

## 43. Quiz aventure

Créer une expérience de questions scénarisées.

Prévoir :

- Une interface immersive.
- Une progression visible et compacte.
- Des réponses faciles à sélectionner.
- Une transition entre les questions.
- Des explications en entraînement.
- Une reprise automatique.
- Un écran final utile.

Ne pas afficher des statistiques inutiles pendant chaque question.

## 44. Vrai ou faux

Créer un mode rapide et dynamique.

Présenter :

- Une affirmation.
- Deux réponses.
- Un feedback.
- Une explication en entraînement.
- Une transition.

Permettre des sessions courtes.

## 45. Associations

Permettre d'associer :

- Des personnages et des événements.
- Des dates et des faits.
- Des symboles et leur signification.
- Des notions et leur définition.
- Des valeurs et des situations.

Prévoir une interface tactile agréable.

Le glisser-déposer ne doit jamais être la seule méthode disponible.

## 46. Frise chronologique

Permettre de remettre des événements dans l'ordre.

Utiliser ce mode notamment pour les contenus historiques.

Prévoir :

- Réorganisation tactile.
- Réorganisation clavier.
- Validation.
- Explication.
- Correction en entraînement.

## 47. Jeu de mémoire

Créer un système de cartes à retourner.

Associer des éléments pédagogiques plutôt que des images purement décoratives.

Exemples :

- Symbole et signification.
- Personnage et réalisation.
- Date et événement.
- Terme et définition.

Adapter la difficulté au nombre de cartes et au contenu disponible.

## 48. Flashcards

Créer des cartes de mémorisation.

Prévoir :

- Une question.
- Une réponse.
- Une explication facultative.
- Une indication de difficulté ressentie.
- Une planification de révision.

Les flashcards doivent être accessibles depuis les cours et les révisions.

Ne pas créer une copie incohérente des contenus existants.

## 49. Texte à compléter

Permettre de mémoriser certains textes.

Prévoir :

- Des mots manquants.
- Des propositions facultatives.
- Une difficulté progressive.
- Une correction autorisée.
- Une comparaison avec le texte original.

Respecter les variantes validées lorsqu'elles existent.

Ne pas inventer les règles de notation officielle.

## 50. Remise en ordre

Permettre de reconstituer :

- Une séquence historique.
- Les étapes d'une procédure.
- Les éléments d'une définition.
- Un texte à mémoriser.
- Une démarche pédagogique.

Prévoir des alternatives accessibles.

## 51. Défis scénarisés

Créer des situations inspirées de la vie scoute.

Exemples :

- Un membre de l'équipe rencontre une difficulté.
- Une activité doit être organisée.
- Une responsabilité doit être assumée.
- Un désaccord apparaît.
- Une mission de service est proposée.

Présenter des choix.

Expliquer leurs conséquences.

Lorsque plusieurs réponses sont raisonnables, ne pas inventer une unique vérité.

Les scénarios doivent être rédigés ou approuvés par l'encadrement.

## 52. Exploration mystère

Créer une expérience dans laquelle l'utilisateur découvre progressivement des indices pour comprendre une notion.

Exemples :

- Identifier un événement historique.
- Découvrir un personnage.
- Comprendre un symbole.
- Reconstituer une histoire.

Chaque indice doit apporter une valeur pédagogique.

Ne pas créer de mystère artificiel qui fait perdre du temps.

## 53. Défi express

Proposer des sessions courtes de quelques questions.

Durées possibles, à titre indicatif :

- 2 minutes.
- 5 minutes.
- 10 minutes.

Ne pas imposer de chronomètre.

Les durées constituent des estimations et non des obligations.

Ce mode doit permettre de réviser rapidement une notion.

## 54. Expédition pédagogique

Créer un mode plus complet regroupant plusieurs types d'interactions.

Exemple :

- Une courte découverte.
- Une énigme.
- Une association.
- Une question de compréhension.
- Une mise en situation.
- Une synthèse.

Chaque expédition doit avoir un objectif pédagogique précis.

Ne pas assembler aléatoirement des jeux sans cohérence.

## 55. Difficulté progressive

Permettre une adaptation de la difficulté en entraînement.

S'appuyer sur :

- Les notions maîtrisées.
- Les réponses précédentes.
- Les erreurs.
- Les exercices déjà rencontrés.
- Les préférences lorsque pertinentes.

Utiliser des règles déterministes.

Ne pas rendre artificiellement les questions difficiles pour prolonger les sessions.

Ne pas modifier la difficulté d'une évaluation officielle publiée sans autorisation métier.

## 56. Mode libre

Permettre aux utilisateurs de choisir un thème et de jouer librement avec les contenus d'entraînement autorisés.

Ne pas limiter l'entraînement aux seules étapes officiellement évaluables lorsque les règles permettent une lecture ou un entraînement libre.

Toute règle d'éligibilité doit respecter les contraintes existantes.

# PARTIE IX — IMMERSION PENDANT LES JEUX ET LES COURS

## 57. Mode concentration

Pendant une expérience pédagogique, masquer les éléments non essentiels.

Ne pas afficher simultanément :

- La sidebar.
- La barre inférieure.
- Les notifications secondaires.
- Les statistiques générales.
- Les widgets.
- Les menus administratifs.
- Les récompenses non pertinentes.
- Les autres modules.

Conserver seulement :

- Un bouton de retour.
- Une progression compacte.
- Le contenu.
- Les interactions nécessaires.
- L'action principale.
- Un indicateur de sauvegarde lorsque pertinent.

Le mode concentration doit être utilisable sur mobile et desktop.

Ne pas forcer le véritable plein écran du navigateur.

## 58. Reprise immédiate

L'utilisateur doit pouvoir quitter une expérience à tout moment, dans les limites des règles d'une évaluation officielle.

Sauvegarder :

- La position de lecture.
- La séquence actuelle.
- Les réponses d'entraînement.
- La progression.
- Les préférences pertinentes.
- Les états autorisés des tentatives.

Permettre la reprise après :

- Fermeture du navigateur.
- Interruption réseau.
- Actualisation.
- Mise en arrière-plan.
- Redémarrage de l'appareil.

Respecter les règles de soumission des évaluations officielles.

## 59. Fin d'expérience

Créer des écrans de fin simples et valorisants.

Afficher uniquement les informations utiles :

- Ce qui vient d'être accompli.
- Les notions éventuellement à revoir.
- Une récompense réellement obtenue.
- La prochaine action possible.

Actions possibles :

- Continuer.
- Revoir.
- Terminer.

Ne pas afficher systématiquement dix statistiques, plusieurs classements et une multitude de boutons.

Ne pas transformer chaque fin de leçon en cérémonie disproportionnée.

# PARTIE X — ENTRAÎNEMENT ET ÉVALUATIONS OFFICIELLES

## 60. Séparation stricte

Tesla doit distinguer deux usages fondamentaux.

### Entraînement libre

L'utilisateur peut :

- Essayer.
- Se tromper.
- Recommencer.
- Obtenir des indices.
- Consulter des explications.
- Réviser.
- Jouer.

### Évaluation officielle

L'utilisateur effectue une tentative soumise aux règles pédagogiques existantes.

L'expérience peut être agréable et immersive.

Cependant, le caractère officiel de la tentative doit être clairement compris avant son démarrage.

Ne jamais masquer cette distinction.

## 61. Banque d'entraînement

Créer ou enrichir une banque d'exercices dédiée à l'entraînement.

Prévoir :

- Les questions.
- Les réponses autorisées.
- Les explications.
- Les sources.
- Les notions associées.
- Les niveaux de difficulté.
- Les modes de jeu compatibles.
- Le statut de publication.
- Les versions.

Ne jamais transformer automatiquement un questionnaire officiel en entraînement si cela expose ses réponses.

Ne jamais récupérer les corrigés officiels pour alimenter un jeu libre.

Préserver les règles d'approbation.

## 62. Évaluations officielles

Conserver strictement :

- Les conditions d'éligibilité.
- Les déblocages.
- Les tentatives.
- Les versions.
- Les réponses.
- Les barèmes.
- Les corrections objectives.
- Les corrections humaines.
- Les résultats.
- Les validations.
- Les droits du responsable plein.
- Les évaluations papier.
- Les règles hors ligne.

Ne pas afficher un corrigé officiel dans le navigateur ou le stockage hors ligne lorsqu'il n'est pas autorisé.

Ne pas fournir d'indice non autorisé.

Ne pas modifier les réponses ou les barèmes.

Ne pas appliquer automatiquement une récompense officielle à partir d'un score ludique.

# PARTIE XI — GAMIFICATION RESPONSABLE

## 63. Principes

La gamification doit soutenir l'apprentissage.

Elle ne doit pas devenir le principal objectif de Tesla.

Ne pas introduire une économie complexe, une boutique, plusieurs monnaies virtuelles ou des dizaines de systèmes de progression.

Créer un système simple à comprendre.

Les récompenses doivent valoriser :

- La découverte.
- La compréhension.
- La mémorisation.
- La persévérance.
- La progression personnelle.
- La coopération.
- La réalisation de missions.

## 64. Points d'expérience

Introduire un système d'XP uniquement si son intégration apporte une valeur réelle.

Les XP peuvent être obtenus lors :

- D'une première découverte.
- D'une leçon terminée.
- D'un entraînement significatif.
- D'une mission accomplie.
- D'une révision utile.
- D'une maîtrise démontrée.

Ne pas récompenser uniquement le temps passé.

Ne pas récompenser indéfiniment la répétition mécanique d'une même action.

Prévoir :

- Une attribution serveur.
- Des événements traçables.
- Des règles configurables.
- Des clés d'idempotence.
- La gestion des versions.
- La validation des événements hors ligne.
- La protection contre les duplications.
- Des tests de concurrence.

Ne pas afficher les XP partout.

Une information compacte peut apparaître lorsqu'une récompense est obtenue.

Le détail reste accessible dans le carnet personnel.

## 65. Niveaux ludiques

Si des niveaux sont introduits, ils doivent être distincts des étapes scoutes.

Ne jamais confondre :

- Niveau d'expérience ludique.
- Étape Route officielle.
- Compétence validée.
- Flot.
- Engagement.
- Départ.

Les appellations ludiques ne doivent pas imiter les grades ou distinctions officielles.

Aucun niveau ludique ne doit bloquer un contenu publié.

## 66. Badges numériques

Créer une collection de badges numériques.

Exemples :

- Premier pas.
- Explorateur des origines.
- Mémoire de la Route.
- Esprit d'équipe.
- Persévérance.
- Curiosité.
- Mission accomplie.
- Maître des repères.

Chaque badge doit posséder :

- Une condition précise.
- Une illustration distinctive.
- Une description courte.
- Une date d'obtention.
- Une attribution traçable.

Éviter les badges accordés sans raison.

Ne pas créer cinquante badges dès le lancement.

Commencer avec un ensemble limité et pertinent.

Prévoir une architecture permettant d'en ajouter ultérieurement.

## 67. Découverte des récompenses

Les récompenses doivent être présentées de manière élégante.

Prévoir :

- Une animation brève.
- Une illustration.
- Une explication courte.
- La possibilité de poursuivre immédiatement.

Ne pas interrompre systématiquement l'apprentissage.

Regrouper les récompenses secondaires lorsqu'elles sont obtenues simultanément.

Ne pas afficher de popup pour chaque XP gagné.

## 68. Engagement sain

Ne pas introduire :

- Des vies limitées empêchant d'apprendre.
- Des pertes de progression pour absence.
- Des séries de connexion punitives.
- Des notifications culpabilisantes.
- Des récompenses financières.
- Des mécanismes de hasard payants.
- Des classements humiliants.
- Des récompenses artificiellement rares.
- Des systèmes conçus pour prolonger compulsivement l'utilisation.

Prévoir des arrêts naturels.

Permettre de reprendre facilement.

Proposer des pauses facultatives après une longue session.

Respecter les préférences de l'utilisateur.

# PARTIE XII — CARNET D'AVENTURE ET RÉVISIONS

## 69. Carnet d'aventure

Faire évoluer la section de parcours personnel pour qu'elle serve de carnet d'aventure.

Réutiliser les pages de progression et de résultats existantes.

Le carnet peut regrouper :

- Le parcours officiel.
- Les connaissances découvertes.
- Les accomplissements.
- Les badges.
- Les activités.
- Les contenus favoris.
- Les notes personnelles.
- Les révisions.
- Les résultats officiels.

Ne pas afficher toutes ces informations sur une seule page.

Organiser les informations de manière contextuelle.

Les détails doivent être accessibles sans encombrer l'interface principale.

## 70. Notes et favoris

Permettre de retrouver rapidement :

- Une notion importante.
- Une leçon favorite.
- Un passage à relire.
- Une note personnelle.

Préserver la confidentialité des notes.

Ne pas donner automatiquement accès aux notes privées à l'encadrement.

Ne pas créer un deuxième système de bibliothèque.

## 71. Répétition espacée

Créer un système de révision déterministe.

S'appuyer sur :

- La date de dernière révision.
- Les erreurs en entraînement.
- Les exercices déjà réalisés.
- La maîtrise ressentie.
- La difficulté des notions.
- Les répétitions précédentes.

Proposer les notions pertinentes au bon moment.

Ne pas imposer un calendrier rigide.

Ne pas envoyer de notifications excessives.

## 72. Révisions personnalisées

Permettre :

- Une révision rapide.
- Une révision thématique.
- Une révision des erreurs.
- Une révision des notions difficiles.
- Une révision par flashcards.

Le système doit éviter de présenter trop souvent les mêmes questions.

Préserver les règles de confidentialité des évaluations officielles.

## 73. Recommandation de prochaine activité

Mettre en place une logique simple permettant de proposer la prochaine activité pertinente.

Priorité indicative :

1. Reprendre une expérience interrompue.
2. Poursuivre un apprentissage commencé.
3. Proposer une révision utile.
4. Découvrir un contenu pertinent.
5. Proposer un défi autorisé.

Une exigence pédagogique ou un rattrapage peut nécessiter une présentation prioritaire selon les règles existantes.

Ne pas présenter plusieurs recommandations concurrentes sur l'accueil.

# PARTIE XIII — MISSIONS ET VIE SCOUTE RÉELLE

## 74. Missions individuelles

Permettre à l'encadrement de proposer des missions.

Exemples :

- Découvrir un thème.
- Préparer une présentation.
- Apprendre une notion.
- Réaliser une recherche.
- Préparer une activité.
- Effectuer un service.
- Réfléchir à une situation.
- Préparer une rencontre.

Une mission doit posséder un objectif clair.

Ne pas introduire un système de gestion de tâches complexe si les structures existantes permettent de répondre au besoin.

## 75. Lien avec le programme annuel

Réutiliser le programme annuel existant.

Associer lorsque pertinent :

- Une activité à un module.
- Une activité à une mission.
- Une activité à des contenus de préparation.
- Une activité à des révisions.

Exemples :

- Préparer une Route en Joie.
- Préparer un camp So'Kraff.
- Préparer un jamboree.
- Préparer une activité de service.
- Préparer une rencontre communautaire.

Ne pas créer de faux événements.

Respecter les données enregistrées par l'encadrement.

Ne pas modifier automatiquement les présences.

## 76. Missions collectives

Exploiter les équipes existantes.

Permettre de proposer :

- Une mission commune.
- Un défi de connaissances.
- Une activité de préparation.
- Un objectif de révision.
- Un exercice de coopération.

Favoriser la fraternité.

Ne pas transformer les équipes en groupes de compétition permanente.

Préserver la possibilité de participer aux activités scoutes sans compte Tesla.

## 77. Jeux collectifs animés par un chef

Étudier et implémenter, si les fondations sont suffisamment solides, un mode permettant à un chef d'organiser une session collective.

Fonctionnement possible :

- Le chef sélectionne un thème.
- Il configure une session.
- Les participants rejoignent via un code temporaire.
- Les questions sont présentées progressivement.
- Le chef anime la session.
- Un bilan pédagogique est disponible.

Utiliser exclusivement des questions d'entraînement autorisées.

Ne pas exposer des résultats officiels.

Prévoir des codes temporaires, une autorisation serveur et une limitation des abus.

Ne pas introduire de téléchargement massif non maîtrisé.

## 94. Synchronisation

Prévoir une file d'attente persistante pour les événements autorisés.

Chaque événement doit disposer :

- D'un identifiant unique.
- D'un type.
- D'une version de contenu.
- D'une référence appropriée.
- D'un état de synchronisation.
- D'une validation serveur.
- D'une stratégie de conflit.

Garantir l'idempotence.

Tester la synchronisation répétée.

Éviter :

- Les doubles récompenses.
- Les doubles tentatives.
- Les réponses perdues.
- Les événements appliqués à un mauvais compte.
- Les conflits silencieux.

Le client peut afficher des états provisoires, mais ne doit pas être considéré comme autorité sur les récompenses ou résultats officiels.

## 95. États hors ligne simplifiés

- Téléchargement en cours.
- Enregistré sur cet appareil.
- Synchronisation en attente.
- Synchronisé.
- Connexion nécessaire.

## 134. Critères d'acceptation UX

L'évolution doit satisfaire les critères suivants :

- L'action principale est identifiable rapidement.
- Aucun écran principal n'est inutilement surchargé.
- Un routier peut reprendre une aventure en une action depuis l'accueil lorsque cela est possible.
- Un jeu peut être lancé sans configuration excessive.
- Une leçon peut être consultée dans son intégralité.
- Les interactions sont intuitives.
- Les animations sont utiles.
- Les informations secondaires ne perturbent pas l'expérience.
- Les textes techniques sont absents de l'expérience apprenant.
- Les fonctions importantes restent accessibles.
- Les interfaces des chefs restent efficaces.

Je veux une application dans laquelle le routier :

- Peut apprendre à son rythme.
- Peut jouer pour comprendre et mémoriser.

- Peut ressentir une progression.
- Peut utiliser Tesla sur son téléphone.

- Peut prendre plaisir à utiliser l'application.

Je veux que l'encadrement puisse créer et administrer les contenus sans difficulté.

Je veux que Tesla possède une véritable identité.

Je veux une application riche en possibilités mais simple dans son apparence.
